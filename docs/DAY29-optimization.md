# День 29. Оптимизация локальной LLM под юридического ассистента

Конкретный кейс проекта — **локальный юридический ассистент**: ответы на вопросы по
кодексам/законам, загруженным как PDF, через RAG (см. [ARCHITECTURE.md](ARCHITECTURE.md)).
Оптимизация ведётся именно под него: точность, опора на источники и предсказуемость
важнее «разговорчивости».

Документ показывает, **как продемонстрировать** каждое требование задания и **чем мерить**
результат. Числовые таблицы заполняются прогоном на вашей машине (нужен запущенный
LM Studio) — см. [Как получить цифры](#как-получить-цифры).

---

## 1. Параметры (temperature, max tokens, context window)

Оптимизированный набор собран в пресет `legal` ([gen_params.py](../gen_params.py), `PRESETS`):

| Параметр | «До» (дефолт модели) | «После» (пресет legal) | Почему так под юр-кейс |
|---|---|---|---|
| `temperature` | пресет модели (часто 0.7–0.8) | **0.0** | закон не терпит креатива: один вопрос → один и тот же ответ |
| `top_k` | — | **20** | узкая выборка токенов, меньше отсебятины |
| `min_p` | — | **0.05** | отсечь совсем маловероятные токены |
| `repeat_penalty` | — | **1.1** | мягкий штраф за повтор формулировок статей |
| `top_p` | — | **0.9** | страховка, если у модели temperature > 0 |
| `max_tokens` | пресет модели | **не задаём** | reasoning-модель тратит на размышления тысячи токенов (~5-7к) до ответа; любой мелкий лимит обрезает её посреди размышлений → пустой ответ. Длину бьёт контекстное окно, а не max_tokens |
| `context_window` | размер из LM Studio | тот же (`/param context_window` при желании) | порог автосжатия истории |

**Как настраивается / демонстрируется в чате:**

```
/param                     # показать текущие параметры модели
/param preset legal        # применить оптимизированный набор
/param preset off          # снять всё → дефолты модели (базовый вариант)
/param context_window 16384  # рабочий лимит контекста для порога сжатия
/param temperature 0.2     # точечно поменять любой параметр
```

**Про context window.** Размер контекстного окна модели задаётся в LM Studio при её
загрузке (по API его можно только прочитать). CLI управляет **использованием** окна:
история хранится в сессии и при заполнении на `COMPRESS_THRESHOLD = 0.8` автоматически
сворачивается в саммари (память + сжатие, см. [ARCHITECTURE.md](ARCHITECTURE.md#сжатие-контекста)).
`/param context_window` задаёт, от какого лимита считать этот порог, — единственный
клиентский параметр, который в API не отправляется.

## 2. Квантование (если доступно)

Квантование — это выбор файла модели (GGUF `Q4_K_M`, `Q5_K_M`, `Q6_K`, `Q8_0`…) в
LM Studio; в коде проекта его не сделать. Демонстрация — **сравнение квантов на одном
наборе вопросов** через тот же бенчмарк:

```
# 1) В LM Studio загрузить квант A (например Q4_K_M), затем:
python bench.py --model <id-Q4> --rag --out docs/bench-q4.md
# 2) Загрузить квант B (например Q8_0), затем:
python bench.py --model <id-Q8> --rag --out docs/bench-q8.md
# 3) Сравнить два отчёта: скорость (ток/с), качество ответов, память (из LM Studio).
```

Что смотреть: более агрессивный квант (Q4) — быстрее и меньше по памяти, но может
терять точность формулировок норм; Q6/Q8 — точнее, но медленнее и тяжелее. Память/размер
модели видны в LM Studio (My Models → размер файла; при загрузке — занятая VRAM/RAM).

| Квант | Размер файла | Память (VRAM/RAM) | Ток/с (bench) | Качество (субъективно) |
|---|---|---|---|---|
| Q4_K_M | _заполнить_ | _заполнить_ | _из bench-q4.md_ | _оценить по ответам_ |
| Q6_K | _заполнить_ | _заполнить_ | | |
| Q8_0 | _заполнить_ | _заполнить_ | | |

## 3. Prompt-шаблон под конкретный кейс

Под юридический Q&A изменены (всё в [chat.py](../chat.py) и [rag.py](../rag.py)):

- **Grounding-инструкция**: «Отвечай, опираясь ТОЛЬКО на пронумерованные фрагменты; если
  ответа нет — напиши "Не знаю", ничего не выдумывай» — против галлюцинаций в юр-ответах.
- **Детерминированный «не знаю»**: при низкой релевантности (`ANSWER_MIN_SCORE`) ассистент
  честно отвечает «не знаю» **без вызова модели** — быстро и без выдумок.
- **Структура ответа**: после ответа печатаются `Источники:` (файл · статья · score) и
  `Цитаты:` — прослеживаемость до нормы.
- **Нарезка по статьям**: `structured_chunks` режет кодекс по «Статья N.», заголовок статьи
  входит в каждый чанк — контекст не теряет привязку к норме.
- **Системный промпт агента** (`LEGAL_SYSTEM` в [chat.py](../chat.py), включается в `/legal on`,
  переиспользуется в bench.py): guardrails юр-ассистента — отвечать фактами и по нормам,
  ссылаться на конкретные статьи и точно цитировать, **не гарантировать исход дела и не
  прогнозировать**, не давать индивидуальных советов и **не заменять живого юриста**,
  предупреждать об изменении норм, ничего не выдумывать.

Демонстрация: `/rag add <кодекс.pdf>`, затем вопрос — виден и ответ, и блок источников/цитат.

## Сравнение: качество, скорость, ресурсы

Два способа — контролируемый (в чате) и воспроизводимый (бенчмарк).

### A. Живой тумблер в чате (быстро показать)

`/legal` — единый переключатель: разом меняет и параметры генерации (пресет `legal`), и
ретривал (`top_k=8` + дедуп по статье), и опору на источники.

```
/legal off   →  задать вопрос  →  посмотреть ответ и дебаг-строку
/legal on    →  тот же вопрос  →  сравнить
```

Наглядный вопрос — «какая статья защищает работника от увольнения?»:
- **off** (top_k=3, без дедупа): в контекст попадают ст. 216.1 и 80 — не те, модель честно
  отвечает «не знаю»;
- **on** (top_k=8, дедуп): в контексте 8 разных норм, включая ст. 81 (защита в отпуске/на
  больничном) и ст. 374 (профсоюзные) — модель отвечает по существу со ссылками.

Дебаг-строка после каждого ответа даёт скорость и расход ресурсов:
```
[18.8 с | промпт 50 + ответ 2024 = 2074 ток. | 107 ток/с | контекст 25% из 8192]
```

Только параметры генерации (без ретривала) — `/param preset legal` / `/param preset off`.

### B. Бенчмарк bench.py (воспроизводимый артефакт)

Гоняет набор вопросов в двух режимах, сводит метрики и сохраняет **сами ответы** для
сравнения качества (markdown + JSON):

```
python bench.py --model <id> --rag                # холистически: до = сырая модель, после = пресет+промпт+RAG
python bench.py --model <id> --rag --isolate      # изолировать эффект ТОЛЬКО параметров
python bench.py --model <id> --rag --repeat 3     # + проверка детерминизма (одинаков ли ответ)
```

- **Качество** — глазами по разделу «ответы по вопросам» (точность, ссылки на нормы,
  отсутствие выдумок) + метрика **детерминизма** при `--repeat > 1` (у пресета legal с
  temperature 0 ответы должны быть идентичны — важное свойство юр-агента).
- **Скорость** — среднее время ответа и ток/с.
- **Ресурсы** — токены промпта/ответа (usage от LM Studio); память/VRAM — из LM Studio.

## Как получить цифры

1. В LM Studio: загрузить модель, **Developer → Start Server**; скачать эмбеддинг-модель
   (напр. `nomic-embed-text`) для RAG.
2. Проиндексировать документ: `python chat.py` → `/rag add C:\путь\кодекс.pdf`.
3. Прогнать бенчмарк:
   ```
   python bench.py --model <id> --rag --repeat 3 --out docs/bench-legal.md
   ```
4. Открыть `docs/bench-legal.md` — оттуда взять числа в таблицы выше; для квантования
   повторить с разными квантами модели.

## Итог

Оптимизированная под юридический кейс локальная LLM: детерминированные параметры
(`preset legal`), управление контекстным окном через память + автосжатие и
`/param context_window`, prompt-шаблон с grounding/«не знаю»/структурой ответа и
нарезкой по статьям. Сравнение «до/после» — воспроизводимо через `bench.py`
(качество по ответам + детерминизм, скорость и расход токенов) и живьём через
переключатель `/param preset off|legal`. Квантование сравнивается тем же бенчмарком
на разных GGUF-квантах.
